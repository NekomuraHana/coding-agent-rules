# Python Coding Rules

この文書は、Python で AI エージェントが実装する際の追加ルールを定義します。  
`common.md` と併用します。

## 1. 基本スタイル

- 既存プロジェクトのフォーマッタ・lint 設定を優先する。
- 新規コードには、可能な範囲で型ヒントを付ける。
- 公開 API と内部実装を区別し、内部用の名前には必要に応じて先頭 `_` を付ける。
- `from module import *` は使用しない。
- mutable default argument を使用しない。

悪い例:

```python
def append_item(item, items=[]):
    ...
```

## 2. 関数と制御フロー

- 深い if ネストよりガード節を優先する。
- 1 関数に複数の独立した責務を詰め込まない。
- 長い処理は、責務の境界で関数へ分割する。
- Boolean だけでは失敗理由が必要十分に伝わらない場合、結果オブジェクト・例外・タプル等を用途に応じて選ぶ。
- 正常系の制御フローを例外だけで表現しない。

## 3. 例外

- `except Exception:` で無条件に握りつぶさない。
- 補足する例外は、可能な限り具体的にする。
- 例外を別の例外へ変換する場合は、元の原因を保持する。
- 回復できない例外を、ログだけ出して正常値へ変換しない。
- cleanup が必要なリソースは `with` または `try/finally` を使用する。

## 4. データ構造

- 単なるデータ集合には、用途に応じて `dataclass`, `NamedTuple`, TypedDict 等を検討する。
- 辞書のキー文字列を多数のモジュールへ散在させない。
- 意味の異なる値を、同じ list / dict へ無理に詰め込まない。
- 状態を持つ必要がない処理を、無理に class にしない。

## 5. モジュール

- import 時に重い副作用を起こさない。
- 循環 import を新たに作らない。
- I/O、外部通信、ハードウェアアクセスと、判定・変換等のロジックを分離する。
- 巨大な utility モジュールを作らない。
- 既存モジュールで表現できる責務のために、安易に新規ファイルを追加しない。

## 6. 型と None

- `None` を返し得る API は型または仕様から分かるようにする。
- `Optional` な値を確認せず利用しない。
- 型チェックを回避するためだけの `Any` を増やさない。
- `# type: ignore` を追加する場合は、その必要性を説明できるようにする。

## 7. 非同期処理

- async API と同期 API を不用意に混在させない。
- coroutine を生成したまま await せず放置しない。
- fire-and-forget が必要な場合は、意図と例外処理方法を明確にする。
- イベントループをブロックする処理を async 関数内へ直接置かない。

## 8. MicroPython 等の制約環境

CPython と異なる制約がある環境では、利用可能な API・メモリ量・実装差を優先する。

- CPython 専用ライブラリを前提にしない。
- 不要な一時オブジェクト生成を増やさない。
- メモリ制約が厳しい環境では、大きな list / dict の常駐を避ける。
- ハードウェア依存処理はアプリケーションロジックから分離する。
- 実機でしか確認できない項目は、未確認であることを報告する。
