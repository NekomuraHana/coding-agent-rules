# C++ Coding Rules

この文書は、C++ で AI エージェントが実装する際の追加ルールを定義します。  
`common.md` と `c.md` を前提とし、この文書には C++ 固有の差分だけを記載します。

`c.md` とこの文書が矛盾する場合は、C++ 固有事項についてはこの文書を優先します。

## 1. リソース管理と所有権

- 所有権を持つリソースは、原則として RAII で管理する。
- 動的メモリの所有権には、生ポインタではなくスマートポインタを使用する。
- 単独所有は原則として `std::unique_ptr` を使用する。
- `std::shared_ptr` は、本当に共有所有が必要な場合だけ使用する。
- 所有権を持たない参照には、参照、ポインタ、`std::span`、`std::string_view` 等を用途に応じて使い分ける。
- `new` / `delete` をアプリケーションコードへ直接散在させない。
- ファイル、mutex、socket、handle 等も、可能な限り RAII オブジェクトで寿命を管理する。

## 2. クラス設計

- Rule of Zero を優先し、デストラクタ・コピー・ムーブ操作を不要に定義しない。
- 特殊メンバ関数を定義する必要がある場合は、コピー可否・ムーブ可否を意識して設計する。
- ポリモーフィックに使用する基底クラスでは、必要に応じて virtual destructor を定義する。
- override する仮想関数には `override` を付ける。
- 継承は「is-a」の関係が明確な場合に限定し、単なるコード再利用のための継承を避ける。
- 継承より合成を優先する。
- クラス内部だけで使用する実装詳細を、不必要に public にしない。

## 3. const と参照

- 変更しない引数・メンバ関数・ローカル値には、必要に応じて `const` を付ける。
- コピーが不要な大きいオブジェクトは、原則として `const T&` 等で受ける。
- NULL を表現する必要がない引数では、ポインタより参照を優先する。
- 参照先や view の寿命が切れた後に使用されないよう、寿命関係を明確にする。
- `std::string_view` や `std::span` を保持する場合は、参照元の寿命を特に確認する。

## 4. 標準ライブラリ

- 独自実装より、目的に合う標準ライブラリ機能を優先する。
- 可変長データには、固定長 C 配列より `std::vector` 等を優先する。
- 文字列には、既存 API との互換性上必要な場合を除き `std::string` 等を使用する。
- 範囲アクセスでは、境界と lifetime を意識する。
- アルゴリズムや range を利用する場合も、単純なループより読みづらくなる使い方は避ける。
- 標準ライブラリ機能の採用時は、プロジェクトの C++ 標準バージョンを確認する。

## 5. キャストと型安全性

- C-style cast は原則として使用しない。
- 通常の型変換には `static_cast` 等、意図が分かる C++ cast を使用する。
- `reinterpret_cast` は、ハードウェアアクセス、ABI、外部 API 等で必要な場合に限定する。
- `const_cast` は、外部 API との互換性等の明確な理由がある場合に限定する。
- 列挙型では、既存コードとの互換性に問題がなければ `enum class` を優先する。

## 6. 例外

- 既存プロジェクトの例外ポリシーを優先する。
- 例外を使用していないプロジェクトへ、局所的な都合だけで新たに例外を持ち込まない。
- 例外を使用する場合、catch 後に握り潰さず、回復・変換・記録等の目的を明確にする。
- デストラクタから例外を送出しない。
- C API、ISR、組み込み境界等をまたいで例外を伝播させない。
- 失敗を戻り値で扱うプロジェクトでは、既存の Result / Status / error code 方針に従う。

## 7. テンプレートとコンパイル時機能

- テンプレートは、型安全性や再利用性に明確な利点がある場合に使用する。
- 単純な処理に過剰な template metaprogramming を導入しない。
- `constexpr` / `consteval` 等は、可読性と対象 C++ 標準を確認して使用する。
- concept が利用可能な場合でも、既存コードが採用していない限り大規模な置き換えを行わない。

## 8. ヘッダと名前空間

- ヘッダ内で `using namespace ...` を使用しない。
- 公開ヘッダへの include 依存を必要最小限にする。
- forward declaration で十分な場合は、不要な include を避ける。
- template や inline 等の理由がない実装は、原則として実装ファイルへ分離する。
- 名前空間は既存プロジェクトの構成に従い、不必要に新しい階層を増やさない。

## 9. 並行処理

- 共有状態は、mutex、atomic 等を用途に応じて明示的に保護する。
- `volatile` をスレッド同期の代用にしない。
- lock の所有範囲を必要最小限にする。
- 複数 lock を使用する場合は、deadlock を避けるため取得順序を明確にする。
- callback や非同期処理へ参照を渡す場合は、対象オブジェクトの寿命を確認する。

## 10. C / ハードウェアとの境界

- C API と接続する箇所では、所有権・寿命・文字列形式・エラーコード変換を境界で明確にする。
- C 互換 API を公開する必要がある場合は、必要に応じて `extern "C"` を使用する。
- MMIO 等の低レベル処理では `c.md` の組み込みルールを適用し、C++ の抽象化によってハードウェア仕様を隠しすぎない。
- 組み込み環境では、RTTI、例外、動的メモリ、標準ライブラリ機能の利用可否をビルド設定と実機制約から確認する。

## 11. テスト

- `c.md` のテスト方針を基本とする。
- ただし、`c.md` に記載された「新規 C 単体テストでは Unity を原則とする」という指定を C++ へ機械的に適用しない。
- 既存の C++ テストフレームワークがある場合は、それを優先する。
- 新しいテストフレームワークを導入する場合は、対象環境・既存ビルド・フットプリントとの整合性を確認する。
- C と C++ が混在するプロジェクトでは、同一のテスト環境を利用できるなら無理に分割しない。
