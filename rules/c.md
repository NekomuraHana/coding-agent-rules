# C Coding Rules

この文書は、C 言語で AI エージェントが実装する際の追加ルールを定義します。  
`common.md` と併用します。

## 1. ヘッダと実装の分離

- `.h` には、外部から利用する型・定数・関数宣言を置く。
- ファイル内部だけで使用する関数・変数は、可能な限り `static` にする。
- 内部実装の都合だけで公開 API を増やさない。
- ヘッダ間の依存を必要最小限にする。
- Include Guard または `#pragma once` は、プロジェクト既存方針に従う。

## 2. メモリと所有権

- バッファの所有者を曖昧にしない。
- 関数が受け取ったポインタを保持する場合、その寿命要件を明確にする。
- 呼び出し側が確保したバッファへ書き込む API を優先する。
- 動的メモリ確保は、プロジェクトで許可されている場合のみ使用する。
- `malloc` / `calloc` / `realloc` を使用する場合は、解放責任を明確にする。
- 解放後のポインタを使用しない。
- 配列やバッファへアクセスする前に、サイズと境界を確認する。

例:

```c
bool get_device_name(char *buffer, size_t buffer_size);
```

戻り値として所有権不明の可変バッファを返す設計は、明確な理由がない限り避ける。

## 3. ポインタ

- NULL を取り得る引数は、API 上またはコメントで明示する。
- NULL を許可しない引数では、既存方針に従って検証または assert を行う。
- 不要な多重ポインタを導入しない。
- 型安全性を損なうキャストを避ける。
- `void *` は、必要な抽象化である場合だけ使用する。

## 4. 戻り値とエラー

- 呼び出し側が処理すべき失敗は、戻り値で明示する。
- 戻り値を無視してよい関数と、確認必須の関数を曖昧にしない。
- 複数の失敗原因を区別する必要がある場合は、enum 等のエラーコードを使用する。
- エラー発生後に部分的な状態変更が残る場合は、その状態を明記またはロールバックする。
- `goto` は、複数リソースの cleanup など終了処理を一本化する用途では許容する。通常の制御フローには使用しない。

## 5. 初期化と状態

- 未初期化変数を使用しない。
- 構造体は必要に応じてゼロ初期化または明示初期化する。
- モジュール初期化前に呼んではいけない API がある場合、その前提を明示する。
- 隠れたグローバル状態への依存を増やさない。
- グローバル変数が必要な場合は、可能な限りファイルスコープ `static` とする。

## 6. 整数とサイズ

- バッファサイズや要素数には、原則として `size_t` を使用する。
- 符号付き / 符号なし整数の暗黙変換に注意する。
- ビット幅が仕様上重要な値には `stdint.h` の固定幅整数型を使用する。
- シフト演算やビットマスクでは、型とビット幅を意識する。
- オーバーフローが仕様上問題になる計算では、演算前に範囲を確認する。

## 7. 組み込み / ハードウェア依存コード

- レジスタ、GPIO、Flash、通信ペリフェラル等への直接アクセスは、HAL / Driver 等の担当層へ集約する。
- Application 層からハードウェア API を直接呼ばない。
- 割り込みハンドラでは、重い処理・ブロッキング処理を避ける。
- ISR と通常コンテキストで共有する状態には、競合を考慮する。
- `volatile` を排他制御の代用にしない。
- ハードウェア依存の定数を、説明なしのマジックナンバーとして散在させない。
- 最適化設定で変数が消える場合があるので、グローバル変数に配置する変数には `volatile`をつける
- RTOSを使用したメモリー確保では、専用関数がある場合もある。存在する場合はそちらを使用する。
- アキュムレータ等のMCUの仕様によっては、ニーモニックに変換した時に演算が正しく行われない場合があるので割り込み禁止を使う。
  - 例) 内部バスが8bitで、扱う数値が32bitにISRが入ると失敗する時がある。

## 8. 禁止・注意パターン

明確な理由がない限り、次を避ける。

- 可変長配列
- 巨大な関数
- 巨大な switch に複数責務を持たせること
- マクロによる複雑な制御フロー
- 副作用を持つ引数をマクロへ渡すこと
- エラーコードを無視すること
- 境界確認なしの文字列・バッファ操作

## 9. テストフレームワーク

### 9.1 テストフレームワークの選択

- プロジェクトですでにテストフレームワークが採用されている場合は、それを優先する。
- 新規に C 言語の単体テスト環境を構築する場合は、原則として Unity を使用する。
  - Unity: https://github.com/ThrowTheSwitch/Unity
- RTOS や SDK が標準または推奨のテストフレームワークを提供している場合は、プロジェクトとの整合性を優先し、そのフレームワークを使用してよい。
- 既存のテスト環境を置き換える目的だけで、新しいテストフレームワークを導入しない。

### 9.2 テストの実行環境

テスト対象ごとに、次の順序で実行方法を検討する。

1. ホスト PC 上で単体テストを実行できる場合は、ホスト上で実行する。
2. QEMU 等の仮想環境が利用可能で、対象機能の検証に適している場合は仮想環境で実行する。
3. ハードウェア依存部分を Mock / Stub で置き換えられる場合は、依存部分を分離してホスト上でテストする。
4. 実ハードウェアが必須の場合は、Target Test / HIL Test として扱う。

実機がないことを理由に、ハードウェアから分離可能なロジックまで未テストのままにしない。

### 9.3 ハードウェア依存コードのテスト

- GPIO、ADC、UART、SPI、I2C 等のハードウェアそのものの動作確認と、それらを利用するアプリケーションロジックの単体テストを分けて考える。
- ハードウェアアクセスは HAL / Driver 層へ分離し、上位ロジックから Mock / Stub に置き換え可能な構造を優先する。
- 実機が必要なテストケースは作成し、通常のホスト単体テストとは区別する。
- 実機環境を利用できない場合は、そのテストを未実行として明示し、テストケース自体を削除しない。
- QEMU 等で周辺機能が十分に再現できない場合、仮想環境の結果を実機試験の代替とはみなさない。

### 9.4 外部入力を扱うロジック

センサー値、通信データ、ADC 値等の外部入力に依存するロジックは、可能な限り Mock / Stub またはテスト用入力を用いて評価する。

最低限、必要に応じて次のパターンを検討する。

- 正常値
- 最小値
- 最大値
- 境界値
- 範囲外の値
- エラー戻り値
- タイムアウト
- 欠損または不完全な入力

入力値を差し替えられない設計になっている場合は、テスト容易性を確保するためにハードウェアアクセスと判定ロジックの分離を検討する。

### 9.5 テスト結果

- 実行したテスト環境が Host / QEMU / Target / HIL のどれであるかを明示する。
- 実行できなかったテストは、その理由を記録する。
- テスト結果の保存と PR / MR への記載方法は `common.md` のルールに従う。
