# Common Coding Rules

この文書は、言語に依存しない実装ルールを定義します。

## 1. 変更の原則

- 要求されていないリファクタリングを行わない。
- 1 回の変更では、原則として 1 つの目的だけを扱う。
- 既存の設計・命名・責務分割を優先する。
- 公開 API を変更する場合は、変更理由と影響範囲を明示する。
- 新しい依存ライブラリを勝手に追加しない。
- 新しい抽象化や共通化は、「将来使うかもしれない」だけを理由に導入しない。

## 2. コードを書く前に確認すること

実装前に、少なくとも次を確認する。

- 変更対象のファイル
- 変更する責務
- 呼び出し元と呼び出し先
- 公開 API への影響
- 既存テストへの影響
- 新規ファイルや新規依存が本当に必要か

大きな変更では、先に変更方針を示してから実装する。

## 3. 責務分離

- 1 モジュール / 1 ファイルには、明確な主責務を持たせる。
- I/O と純粋なロジックを可能な範囲で分離する。
- ハードウェア依存処理は、アプリケーションロジックから分離する。
- 下位層から上位層を参照しない。
- グローバル状態をモジュール間の暗黙的な通信手段にしない。
- 既存ディレクトリで表現できる責務のために、新しいディレクトリを増やさない。
- ディレクトリ構成として、1つのディレクトリには同系統の処理系をまとめるようにする。
- 1ファイルには同系統の処理系を集約するようにする

## 4. 関数

- 1 関数には 1 つの主要な責務を持たせる。
- 深いネストを避け、ガード節を優先する。
- 呼び出し側が必要とする失敗理由を失わない。
- 副作用のある処理は、関数名またはインターフェースから判別できるようにする。
- 真偽値だけでは原因を表現できない失敗を、無理に `true / false` だけで表さない。
- 相互再帰や自己再帰にならないようにする。

## 5. 命名

- 名前は役割・機能を表し、実装方法だけを名前にしない。
- 関数名は、原則として「動詞 + 対象」とする。
- 関数名は短縮化をさせずに記載をする。
- Boolean 値は `is_`, `has_`, `can_`, `should_` など、真偽が分かる名前を使う。
- 同じ概念に複数の用語を使わない。
  - 設定系は `config_`
  - 初期設定値系 `default_`
  - 更新系は `update_`
  - 削除系は `delete_`
  - 長さに関することは次の通り
    - 個数に関わること、もしくはタイマー系には `count_`
    - ペイロードデータなど、一定の長さがあって意味を成す場合は `length_`
- プロジェクト固有の用語は、必要に応じて用語集に定義する。

## 6. エラー処理

- エラーを握りつぶさない。
- 復旧可能なエラーと、プログラム上の不整合を区別する。
- リトライには上限または終了条件を設ける。
- ログだけ出して正常終了扱いにする場合は、その意図を明確にする。
- 失敗時に中途半端な状態を残さない。

## 7. コメント

- コードを読めば分かる処理内容を、そのままコメントに書かない。
- 「何をしているか」より「なぜそうしているか」を優先する。
- 仕様上の制約、ハードウェア制約、互換性維持の理由など、コードだけでは分からない判断を残す。
- コードとして分かりにくいのは、制御・ステートマシン・計算式として複雑な所で発生しやすいので気をつける。
- 古くなったコメントは残さない。

## 8. テストと検証

- 変更した振る舞いには、可能な範囲でテストまたは再現手順を用意する。
- 既存テストを理由なく削除・無効化しない。
- テストを通すためだけに本番コードの意味や機能を変えない。
- 実行できなかったテストや未確認事項は明記する。
- テストコードと、本番コードはディレクトリ単位で分けること。
- テストはテストフレームワークを使用すること。
- テスト結果がAI上で取得できる場合、結果のテキストデータをテキストデータで格納すること

## 9. AI エージェント向け禁止事項

AI エージェントは、明示的な依頼がない限り次を行わない。

- 大規模なリファクタリング
- 公開 API の変更
- ディレクトリ構造の再編
- 外部依存の追加
- ビルド方式の変更
- テストの削除・無効化
- 既存コード全体へのフォーマット変更
- 「より一般的にする」ことだけを目的とした抽象化

## 10. 変更後に報告すること

実装後は、少なくとも次を示す。

- 変更したファイル
- 変更内容
- 外部仕様への影響
- 実行したテスト / ビルド
- 未確認事項または既知の制約

## 11. gitのコミット単位について

- 機能単位でのコミットをすること

## 12. プルリクエスト・マージリクエストについて

- 行ったことについて記載をする
  - コーディングした範囲とファイルの一覧
  - テストの実行の有無について
  　- テストを実行した場合の結果ファイルの場所の記載
- 未完了の箇所についてを一覧で記載
