# Documentation Rules

この文書は、AI エージェントが README、仕様書、設計資料、API 説明、手順書などの技術文書を作成・変更する際の追加ルールを定義します。  
`common.md` と併用します。

## 1. 文書変更の原則

- 既存文書の目的、対象読者、構成、文体を尊重する。
- 要求されていない全面的な書き換えや再構成を行わない。
- 表現の改善だけを目的として、技術的な意味を変更しない。
- 既存の情報を、不要と判断しただけで勝手に削除しない。
- 同じ文書内では、用語、表記、見出しの粒度を可能な限り統一する。
- 変更は必要最小限とし、文書全体への不要なフォーマット変更を避ける。

## 2. 事実と推測の区別

- 根拠のない仕様、制約、数値、対応環境を追加しない。
- 不明な事項を推測で補完しない。
- 実装から読み取った挙動を、正式な仕様として断定しない。
- 未確認事項は、必要に応じて「未確認」「要確認」「推定」などと明示する。
- AI の一般知識だけを根拠として、プロジェクト固有の仕様を作成しない。
- 仕様、実装、検証結果、推測を混同しない。

AI エージェントは文書の編集者であり、仕様の発明者ではない。

## 3. 文書構造

- 見出しレベルは順序を守る。
- 1 セクションでは、原則として 1 つの主題を扱う。
- 同じ内容を複数箇所へ重複して記載しない。
- 長い文書では、概要から詳細へ進む構成を優先する。
- 既存の文書構成で表現できる場合は、不要なファイル分割を行わない。
- 詳細情報が別文書に存在する場合は、同じ内容を複製せず参照先を示す。

## 4. 用語と表記

- 同じ概念には、原則として同じ用語を使用する。
- プロジェクト固有の用語や既存の名称を、理由なく別の表現へ置き換えない。
- 略語は、対象読者にとって必要な場合は初出時に正式名称を併記する。
- 規格名、API 名、製品名、型番などは正式な表記を優先する。
- 単位を伴う値では、単位を明記する。
- 数値の意味が重要な場合は、条件や基準も併記する。

## 5. 使用する IC・部品・モジュール

ハードウェアを含むプロジェクトの文書では、実装や設計の理解に必要な IC、部品、モジュール、評価ボード等を明記する。

可能な範囲で、次を記載する。

- メーカー名
- 正式な型番または製品名
- プロジェクト内での役割
- 使用するインターフェース
- 実装へ影響する電圧、クロック、アドレス、ピン等の条件
- 必要に応じてパッケージ、リビジョン、ボード版数
- データシート、リファレンスマニュアル、製品ページ等の参照先

部品の状態も可能な限り区別する。

- 採用済み
- 採用予定
- 候補
- 評価中
- 置き換え予定

型番が不明な場合は推測で補完せず、不明であることを明示する。

類似型番、同一シリーズ、後継品を、確認なしに同一仕様として扱わない。

## 6. Markdown の記述

- GitHub Flavored Markdown で問題なく表示できる形式を基本とする。
- 見出し、箇条書き、表、コードブロックを用途に応じて使い分ける。
- コードブロックには、可能な場合は言語指定を付ける。
- 表は比較や対応関係の整理に有効な場合のみ使用する。
- 横幅が過度に大きくなる表は避ける。
- 装飾だけを目的とした HTML の使用を避ける。
- Markdown の記法自体を複雑化しない。

## 7. コード・コマンド・設定例

- 実在を確認できない API、コマンド、オプションを例として作成しない。
- サンプルコードと実製品で使用するコードを区別する。
- コピーして実行することを想定したコマンドでは、置換が必要な値を明確にする。
- 危険な操作や不可逆な操作には、必要に応じて注意事項を記載する。
- 実行結果を例示する場合は、実測値と説明用の例を区別する。
- バージョンに依存する手順では、対象バージョンを可能な範囲で明記する。

## 8. 図・Mermaid

- 文章だけでは構造、関係、処理の流れを理解しにくい場合に使用する。
- 図と本文の内容を矛盾させない。
- ノード名、矢印、用語の意味を文書内で一貫させる。
- 重要な仕様を図だけに記載せず、必要な内容は本文にも残す。
- 実装されていない構成を、現在の構成として図示しない。

## 9. リンクと参照資料

- 外部仕様や規格を根拠とする場合は、可能な範囲で参照先を残す。
- リンクだけを置かず、何を参照する資料なのか分かるようにする。
- バージョン依存の仕様では、対象となる版やバージョンを可能な範囲で記載する。
- 存在を確認できない URL を生成しない。
- 一次資料が利用できる場合は、まとめサイト等より一次資料を優先する。
- リンク先の内容と本文で引用・要約した内容が一致することを確認する。

## 10. README

README では、プロジェクトを初めて見る人が概要と利用方法を理解できることを優先する。

必要に応じて次を記載する。

- プロジェクトの目的
- 主な機能
- 必要な環境
- 使用する主要な IC、モジュール、ライブラリ等
- セットアップ方法
- 基本的な使い方
- ビルド、実行、テスト方法
- 詳細資料への参照

詳細な内部仕様や設計情報を README に集中させすぎず、必要に応じて別文書へ分離する。

## 11. AI エージェント向け禁止事項

AI エージェントは、明示的な依頼または十分な根拠がない限り次を行わない。

- 存在しない仕様の補完
- 未確認事項の断定
- 文書全体の無断再構成
- 技術的な意味を変える文章の簡略化
- プロジェクト固有用語の勝手な言い換え
- 根拠のない性能値、制限値、対応環境の追加
- 未確認の IC、部品、型番、ピンアサインの追加
- 架空または未確認のリンクの追加
- 現在の実装と将来案の混同

## 12. 変更後に確認すること

文書変更後は、少なくとも次を確認する。

- 技術的な意味が変更前後で意図せず変わっていないか
- 用語や型番に表記揺れがないか
- 本文、表、図の内容が矛盾していないか
- コード例、コマンド、リンクに明らかな誤りがないか
- 未確認事項を断定していないか
- 文書の対象読者に対して必要な情報が不足していないか
